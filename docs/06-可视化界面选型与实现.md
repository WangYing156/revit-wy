# 可视化界面：载体选型与实现

> 你的问题：「考虑一下可视化界面，Revit 能否搭载」
> **最终决策：采用 D 方案（浏览器 + 本地服务）作为可视化主载体。**
> Revit 2022 停靠面板保留，但只做 Revit 原生的事（选中/清理），不再重复实现可视化。
>
> 本文记录选型理由、D 方案的完整能力，以及为什么在四种载体里选它。

---

## 一、先回答"能不能"

Revit 插件（`IExternalApplication`）本身就是 .NET WPF 应用程序，**任何 WPF 能放的控件它都能放**。
所以"能不能搭载可视化界面" —— 能，而且不受限。

真正的问题变成：**放在哪、用谁做前端、崩了谁负责**。

---

## 二、四种载体对比

| 载体 | 能力 | 与 Revit 集成度 | 主要风险 | 适用 |
|---|---|---|---|---|
| **A. 停靠面板（DockablePane + WPF）** | 表格、下拉、简单图形 | 高：可常驻、可读选中集、可直接建构件 | 低。WPF 在 Revit 里已用十几年 | **人在 Revit 里操作的场景** ✅ |
| **B. 停靠面板 + WebView2** | 任意 HTML/Canvas/框架 | 高 | **高**：见下方实测风险 | 已经有一套 Web 前端要复用 |
| **C. 独立 WPF 窗口** | 同 A，但浮动 | 中 | 低，但易被主窗口遮挡 | 一次性大操作面板 |
| **D. 浏览器独立页（本地服务）** | 任意 Web 能力 | 低：不碰 Revit | 极低 | **改规则/调参数的迭代场景** ✅ |

### 最终选择：D（浏览器 + 本地服务）

**理由（按权重排序）**

1. **翻模的瓶颈是循环速度，不是界面美观**
   真实工作是「改一张图 → 调规则 → 看识别对不对 → 再调」，一天几十次。
   浏览器方案把这个循环压到「改一个数 → 秒级看到结果」，且不需要开 Revit。

2. **零插件依赖**
   不装 Revit 也能审图、调规则、出对照单。这让"图纸能不能翻模"这个判断可以
   前置到投标/评审阶段，不用等建模组排期。

3. **同一套后端，不会出现"两套逻辑两套结果"**
   工作台、MCP、CLI 全部调 `mapping / ir / diffing` 同一份代码。
   如果另做一套 C# 侧可视化，规则判定就有两个实现，迟早不一致。

4. **可远程**
   同事在自己电脑上开浏览器就能看你生成的对照单，不需要装软件。

5. **零前端构建**
   单文件 HTML + Canvas，不用 npm/node。设计院离线环境、受限网络都能跑。

**代价与应对**

| 代价 | 应对 |
|---|---|
| 需要额外起一个本地服务 | `revit-wy panel` 一条命令；与 MCP 是同一个 Python 环境 |
| 浏览器与 Revit 之间不能直连（CORS） | 由本地服务代理：浏览器 → 服务 → Revit 插件 |
| 不能直接在浏览器里操作 Revit 视图 | 通过 `select_by_tags` 协议让 Revit 选中/缩放，体验已足够 |

### 为什么停靠面板不重复做可视化

我在设计前查证了 WebView2 在 Revit 里的实际表现，结论是**不值得**：

| 实测/已知问题 | 后果 | 来源 |
|---|---|---|
| 关闭 Revit 时抛 `CoreWebView2 members cannot be accessed after the WebView2 control is disposed` | 每次退出 Revit 都弹异常，用户以为插件坏了 | WebView2 反馈区 #2631 |
| 从 WebView2 回调里调 `doc.LoadFamily()`（家族升级时） | **WebView2 永久失效**，`EnsureCoreWebView2Async` 挂死，只能重启 Revit | Autodesk 论坛 2023 |
| Revit 的渲染与 WPF 存在空域（airspace）冲突 | 控件偶发空白/不刷新，需要 `CompositionControl` 变通，而后者在 Revit 里又不渲染 | WebView2 反馈区 #5189 |
| `Microsoft.Web.WebView2.dll` 版本与 Revit 自带的不一致 | `0x8007007E` 加载失败 | Autodesk 论坛 2024 |
| 需要额外部署 `WebView2Loader.dll` 与 x64 RuntimeIdentifier | WiFi 受限环境部署复杂度上升 | 同上 |

**而面板真正要做的事情，纯 WPF 完全够：**

- 列图层、显示实体数、显示置信度 → `DataGrid`
- 改归属 → `ComboBox`
- 看模型对不对 → **直接用 Revit 自己的三维视图高亮**（比在面板里画一份平面更权威）

> 这不是"技术保守"，是**权衡后主动放弃**：为了一个更好看的 UI，引入四条已知的崩溃路径，
> 而收益只是"表格换个皮肤"，不划算。

**什么时候我会改选 B**：如果你已经有一套 Web 版翻模平台要复用前端，
那 WebView2 的代价可以通过"只做只读展示、绝不在网页回调里调 Revit API"来压低。
这时可以考虑，但要接受偶发空白的运维成本。

## 三、D 方案的能力清单

启动：

```powershell
revit-wy panel samples\arch_plan.dxf          # 默认 8770，自动连 Revit 48880
# 或指定端口 / 专业
revit-wy panel D:\drawings\F1.dxf -p struct --port 8770 --revit-port 48880
```

打开 `http://127.0.0.1:8770/`，得到 5 个页签：

| 页签 | 能力 | 解决什么问题 |
|---|---|---|
| **图层** | 图层清单 + 归属下拉 + 点行隐藏 | 一眼看出每层被判成什么，改完立即重算 |
| **构件** | 墙/柱/梁/门/窗/板/轴网逐个列出，**点一行 → 图上高亮 + Revit 里选中缩放** | "这个构件到底对不对" |
| **差异** | 与上次写入的模型比对：新增/删除/改动 | **改图重跑前先确认会影响哪些构件** |
| **规则** | 层高、墙厚、板厚、门窗尺寸热改 | 试参数不用改 yaml 再重启 |
| **导出** | 一次导出 md/csv/json/yaml | 留档、发给复核人 |

### 3.1 画面

- **Canvas 渲染 CAD 原图**：按图层分色，建模层亮色、隔离层暗灰
- **识别结果叠加**：墙按真实厚度画带宽线、柱按旋转角画矩形、门窗画圆、轴网虚线、楼板半透明填充
- **三种视图**：CAD 原图 / 原图+识别 / 仅识别
- **点构件选中**：命中容差 = 屏幕 8px + 构件半宽，点墙的边也算选中

### 3.2 两个关键实现决策

**① 差异对比按「几何签名」，不按 id**

这是个必须绕开的坑：IR 里的 id 是每次运行随机生成的（`wall-3f2a1c9e04`），
按 id 比对**永远得到"全部新增、全部删除"**——看起来能用，实际完全没用。

改用几何不变量做签名：

| 构件 | 签名构成 | 容差处理 |
|---|---|---|
| 墙 / 梁 | 两端点量化到 2mm + 排序（**与绘制方向无关**）+ 厚度 | 反向画的同一面墙正确判为相同 |
| 柱 | 中心 + 截面（b/h 排序）+ 旋转角 **归一到 [0,90)** | 旋转 90° 判为相同 |
| 门窗 | 中心 + 宽度 | |
| 板 | 轮廓点排序哈希 + 厚度 | |

再加一层"位置对得上但尺寸不同 → 判为改动（modified）而不是删+增"，
移动容差 300mm。这样报出来的数字更贴近人的直觉：**改了一道墙厚，就报「改动 1」而不是「删 1 加 1」**。

**② 浏览器不能直连 Revit，由本地服务代理**

```
浏览器 ──HTTP──► 本地服务 :8770 ──TCP NDJSON──► Revit 插件 :48880
```

浏览器直接连 `127.0.0.1:48880` 有两个问题：跨域（CORS）会被拦；
TCP 裸协议浏览器也发不了。所以探测、写入、选中全部走服务端代理，
前端只调同源 HTTP 接口。

### 3.3 安全闸

写入 Revit 是**两段式**，防误触：

```
点「写入 Revit」
  → 服务端 dry_run=true：返回"将要创建什么"（不写任何东西）
  → 浏览器弹确认框：标高 2 · 轴网 5 · 墙 5 · 柱 0 …
  → 用户点确定
  → dry_run=false + confirm=true 才真正写入
```

服务端也会独立校验：缺 `confirm` 一律拒绝。所以哪怕前端被绕过，
后端这层闸门依然有效。

## 四、Revit 停靠面板（保留，但只做原生的事）

D 方案定了之后，面板的职责收窄为「只有 Revit 才能做的事」：

| 功能 | 为什么必须在 Revit 里做 |
|---|---|
| 选中并缩放到翻模构件 | 需要 `Selection` + `ShowElements`，浏览器做不到 |
| 清理上次翻模的构件 | 需要事务删除，且只删带 `revit-wy:` 标记的 |
| 查看端口/连接状态、重启服务 | 插件自身诊断 |
| 打开日志 | 排错 |

面板里**不再画平面、不再做图层确认**——那些都在浏览器里做，避免两套 UI 两处维护。

## 五、下一步可以做什么

按投入产出排序：

| 优先级 | 能力 | 做法 | 投入 |
|---|---|---|---|
| ⭐⭐⭐ | **差异对比视图** | 两次 IR 叠加，改动的墙标红 | 小：前端加一层 diff 渲染 |
| ⭐⭐⭐ | **构件表格 + 跳回 Revit** | 点表格某行 → Revit 选中该构件 | 小：HTTP 回调 + `ShowElements` |
| ⭐⭐ | 图层映射实时编辑 | 面板里直接改 yaml 规则，不只改单层归属 | 中：需要写 yaml 回存 |
| ⭐⭐ | 三维预览（三.js） | IR 转 glTF，浏览器里转到 3D | 中：需要引入三维库（违背零依赖） |
| ⭐ | WebView2 全功能面板 | 复用 Web 前端 | 大：要处理本文第二节的全部风险 |
| ⭐ | 移动端查看 | 同上，改响应式 | 大：价值不明确 |

我的建议：**先做前两项**。它们直接服务于"确认得对不对"这个核心痛点，
而三维预览在建模完成前意义不大——那时候你已经能在 Revit 里看真模型了。

| 项 | 状态 |

| 点构件 → Revit 选中 | ✅ `select_by_tags` 返回 selected=1 |
| 差异签名（反向墙/旋转柱） | ✅ 判为"未变化"，不误报 |
| 导出确认单 4 件套 | ✅ 落盘到 `<图纸名>/review/` |
| C# 20 个文件语法 | ✅ 通过 |
| XAML | ✅ XML 良构 |
| JS | ✅ node --check 通过 |
| 测试总数 | ✅ 38 项全绿 |

**本轮修掉的两个真实缺陷**

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | 差异对比按随机 id 比对 | 永远"全新增"，功能形同虚设 | 改按几何签名（`diffing.py`），反向墙/旋转柱正确识别 |
| 2 | 别名只在"规则也命中"时生效 | **用户确认"这层隔离"后毫无效果**，整个数模对照环节形同虚设 | 别名短路到 `match()` 最前，且支持 isolate/ignore 这类动作型归属 |

> 第 2 个缺陷影响最大——它会让"确认"这个核心动作完全失效，而表面上没有任何报错。
> 现在有 5 项回归测试锁死，改回旧逻辑测试会立刻失败。

⚠️ **仍需你在 Windows 上验证的**：C#/XAML 的**语法**在这里校验通过，但 WPF 面板的
实际渲染、以及 `select_by_tags` 在真实 Revit 里的选中效果，必须在装了 Revit 2022 的
机器上跑一次才能确认。
