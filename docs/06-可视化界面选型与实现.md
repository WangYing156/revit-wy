# 可视化界面：载体选型与实现

> 你的问题：「考虑一下可视化界面，Revit 能否搭载」
> 结论：**能搭载，而且 Revit 2022 给了三条路，但其中最好看的那条恰恰最危险。**
> 本文说清楚每种载体各自的代价，以及我最终做了什么。

---

## 一、先回答"能不能"

Revit 插件（`IExternalApplication`）本身就是 .NET WPF 应用程序，**任何 WPF 能放的控件它都能放**。
所以"能不能搭载可视化界面" —— 能，而且不受限。

真正的问题变成：**放在哪、用谁做前端、崩了谁负责**。

---

## 二、四种载体对比

| 载体 | 能力 | 与 Revit 集成度 | 主要风险 | 适用 |
|---|---|---|---|---|
| **A. 停靠面板（DockablePane + WPF）** | 表格、下拉、简单图形 | 高：可常驻、可读选中集、可直接建构件 | 低。WPF 在 Revit 里已用十几年 | **人在 Revit 里操作的场景** ✅ |
| **B. 停靠面板 + WebView2** | 任意 HTML/Canvas/框架 | 高 | **高**：见下方实测风险 | 已经有一套 Web 前端要复用 |
| **C. 独立 WPF 窗口** | 同 A，但浮动 | 中 | 低，但易被主窗口遮挡 | 一次性大操作面板 |
| **D. 浏览器独立页（本地服务）** | 任意 Web 能力 | 低：不碰 Revit | 极低 | **改规则/调参数的迭代场景** ✅ |

### 关键判断：为什么 A+D 组合，而不是 B

我在设计前查证了 WebView2 在 Revit 里的实际表现，结论是**不值得**：

| 实测/已知问题 | 后果 | 来源 |
|---|---|---|
| 关闭 Revit 时抛 `CoreWebView2 members cannot be accessed after the WebView2 control is disposed` | 每次退出 Revit 都弹异常，用户以为插件坏了 | WebView2 反馈区 #2631 |
| 从 WebView2 回调里调 `doc.LoadFamily()`（家族升级时） | **WebView2 永久失效**，`EnsureCoreWebView2Async` 挂死，只能重启 Revit | Autodesk 论坛 2023 |
| Revit 的渲染与 WPF 存在空域（airspace）冲突 | 控件偶发空白/不刷新，需要 `CompositionControl` 变通，而后者在 Revit 里又不渲染 | WebView2 反馈区 #5189 |
| `Microsoft.Web.WebView2.dll` 版本与 Revit 自带的不一致 | `0x8007007E` 加载失败 | Autodesk 论坛 2024 |
| 需要额外部署 `WebView2Loader.dll` 与 x64 RuntimeIdentifier | WiFi 受限环境部署复杂度上升 | 同上 |

**而面板真正要做的事情，纯 WPF 完全够：**

- 列图层、显示实体数、显示置信度 → `DataGrid`
- 改归属 → `ComboBox`
- 看模型对不对 → **直接用 Revit 自己的三维视图高亮**（比在面板里画一份平面更权威）

> 这不是"技术保守"，是**权衡后主动放弃**：为了一个更好看的 UI，引入四条已知的崩溃路径，
> 而收益只是"表格换个皮肤"，不划算。

**什么时候我会改选 B**：如果你已经有一套 Web 版翻模平台要复用前端，
那 WebView2 的代价可以通过"只做只读展示、绝不在网页回调里调 Revit API"来压低。
这时可以考虑，但要接受偶发空白的运维成本。

## 三、我实际做了什么

两件东西，分别服务两种场景：

```
┌─────────────────────────────────────┐     ┌──────────────────────────────────┐
│ 场景 1：改图纸、调规则、看识别对不对    │     │ 场景 2：人在 Revit 里确认并下发    │
│ 载体：浏览器 + 本地服务                │     │ 载体：Revit 停靠面板（纯 WPF）      │
├─────────────────────────────────────┤     ├──────────────────────────────────┤
│ tools/viewer/  （Canvas 画图，零依赖）  │     │ addin/.../UI/WyDockablePane.xaml  │
│                                       │     │                                  │
│ · 原图 + 识别结果叠加                  │     │ · 图层表格 + 归属下拉              │
│ · 点图层隐藏/高亮                      │     │ · 双击快速切 建模/隔离             │
│ · 下拉直接改归属 → 立即重算            │     │ · 应用到 Revit（下发到 Python）    │
│ · 改建模规则 → 立即重算                │     │ · 清理上次翻模                    │
│ · 一天跑几十次，秒级反馈                │     │ · 在三维视图里高亮 + 缩放到构件     │
└─────────────────────────────────────┘     └──────────────────────────────────┘
                    │                                        │
                    └────────────── 同一个后端 ──────────────┘
                        （tools/viewer/server.py，端口 8770）
```

### 3.1 场景 1：本地预览服务

```powershell
# 启动（会自动加载样例图）
revit-wy panel samples\arch_plan.dxf

# 打开 http://127.0.0.1:8770/
```

功能：

- **Canvas 渲染 CAD 原图**：按图层分色，建模层亮色、隔离层暗灰
- **识别结果叠加**：墙按厚度画带宽线、柱按旋转角画矩形、门窗画圆、轴网虚线、楼板半透明填充
- **三种视图模式**：CAD 原图 / 原图+识别 / 仅识别（点右上按钮循环切换）
- **图层面板**：每行显示颜色点、图层名、实体数、识别结果、置信度条、归属下拉
- **点行隐藏该图层**，方便定位"这批线到底是哪层的"
- **改归属立即重算**，并写入别名库（和 AI 走同一个状态）
- **改建模规则立即重算**（层高、墙厚、板厚、门窗默认尺寸）

为什么用本地服务而不是直接生成一张静态 SVG：
**"改一点 → 看一眼"的循环需要秒级反馈**。静态图每次都要重跑脚本、重新打开文件，循环成本高一倍。

数据量处理：单层 3000 段、全局 45000 段上限，超了会标注"已限流"。
真实平面图常 10 万图元，全量传浏览器会卡死；按"每层限量 + 长线优先"能保留结构信息而丢掉碎线。

### 3.2 场景 2：Revit 停靠面板

```
功能区 revit-wy → [翻模面板] [连接状态] [清理上次翻模] [重启服务] [打开日志]
                        ↓
面板（停靠在项目浏览器旁）
┌──────────────────────────────────┐
│ ● MCP 服务运行中 · 127.0.0.1:48880 │
│ 文档：某住宅项目.rvt               │
├──────────────────────────────────┤
│ 数模对照 · 图层归属                 │
│ [刷新图层] [预览高亮] [应用到 Revit] │
│ [清理上次翻模的构件]                │
├──────────────────────────────────┤
│ ●  A-WALL      1284   [墙 ▾]  98% │
│ ●  墙体 200     412   [墙 ▾]  90% │
│ ●  图层1        204   [待确认▾] 0% │  ← 橙色高亮
│ ●  A-FURN        88   [隔离 ▾] 90% │
├──────────────────────────────────┤
│ 共 8 个图层 ｜ 建模 5 · 待确认 1 …  │
└──────────────────────────────────┘
```

技术要点（都踩过）：

| 要点 | 说明 |
|---|---|
| `RegisterDockablePane` 只能在 `OnStartup` 调用一次 | 重复注册抛异常 |
| 注册后**不会自动显示** | 必须 `uiApp.GetDockablePane(id).Show()`，所以功能区要有按钮 |
| 面板实例必须**静态持有** | 否则被 GC 后变空白 |
| 用 `UserControl` 而非 `Page` | Page 需要 NavigationService，DockablePane 里容易出问题 |
| 面板里不做图纸解析 | ezdxf 的能力在 C# 没等价物，通过 HTTP 复用 Python 侧 |
| **不自动轮询** | Revit 里轮询占 UI 线程，改成点"刷新" |

### 3.3 一个刻意的设计：预览用 Revit 自己的三维视图

面板上的「预览高亮」按钮做的事是：

```csharp
var ids = WyBackend.CollectTaggedIds(doc);   // 所有带 revit-wy 标记的构件
uidoc.Selection.SetElementIds(ids);          // 选中
uidoc.ShowElements(ids);                     // 缩放到选中集
```

而不是在面板里再画一遍平面。理由：

1. **权威**：Revit 三维视图就是最终结果，面板画的是"中间产物"，看它没意义
2. **零成本**：一行 API，不用维护两套渲染
3. **可交互**：选中后能直接改、能量、能出剖面

配合"按 Comments 参数过滤"的可见性设置，能一眼区分翻模构件和手工构件。

## 四、如果你想要更强的可视化，下一步可以做什么

按投入产出排序：

| 优先级 | 能力 | 做法 | 投入 |
|---|---|---|---|
| ⭐⭐⭐ | **差异对比视图** | 两次 IR 叠加，改动的墙标红 | 小：前端加一层 diff 渲染 |
| ⭐⭐⭐ | **构件表格 + 跳回 Revit** | 点表格某行 → Revit 选中该构件 | 小：HTTP 回调 + `ShowElements` |
| ⭐⭐ | 图层映射实时编辑 | 面板里直接改 yaml 规则，不只改单层归属 | 中：需要写 yaml 回存 |
| ⭐⭐ | 三维预览（三.js） | IR 转 glTF，浏览器里转到 3D | 中：需要引入三维库（违背零依赖） |
| ⭐ | WebView2 全功能面板 | 复用 Web 前端 | 大：要处理本文第二节的全部风险 |
| ⭐ | 移动端查看 | 同上，改响应式 | 大：价值不明确 |

我的建议：**先做前两项**。它们直接服务于"确认得对不对"这个核心痛点，
而三维预览在建模完成前意义不大——那时候你已经能在 Revit 里看真模型了。
