# 支持 Revit 2022 及以上：多版本策略与兼容层

> 需求变更：原定"只做 Revit 2022"，现改为 **2022 及以上**。
> 本文说明哪些地方必须改、为什么、以及怎么验证。

---

## 一、先搞清楚"支持多版本"到底难在哪

Revit 不是"一个 API 加几个新类"，它在 **2024→2025 之间换过一次运行时**，
这一刀把插件生态切成了两条互不兼容的线：

| Revit | 发布 | 插件必须编译到 | ElementId 存储 |
|---|---|---|---|
| 2022 | 2021-04 | `net48` | int32 |
| 2023 | 2022-04 | `net48` | int32 |
| 2024 | 2023-04 | `net48` | int32（`IntegerValue` 标 Obsolete） |
| 2025 | 2024-04 | `net8.0-windows` | int64（`IntegerValue` 抛异常） |
| 2026 | 2025-04 | `net8.0-windows` | int64 |
| 2027+ | 预计 | `net10.0-windows` | int64 |

**最坑的一点**：编译到错误的运行时，**Revit 什么错都不报**——
插件被静默跳过，功能区连按钮都不出现，也没有日志可看。
所以"支持多版本"的第一原则是：**版本和 DLL 必须一一对应，绝不能混放。**

## 二、改动清单

### 2.1 工程文件：按版本决定目标框架

`addin/RevitWy.Plugin/RevitWy.Plugin.csproj` 用 `RevitVersion` 驱动一切：

```powershell
dotnet build addin/RevitWy.Plugin -c Release -p:RevitVersion=2024   # → net48
dotnet build addin/RevitWy.Plugin -c Release -p:RevitVersion=2025   # → net8.0-windows
```

内部规则：

```xml
<TargetFramework Condition="'$(RevitVersion)' &lt; '2025'">net48</TargetFramework>
<TargetFramework Condition="'$(RevitVersion)' == '2025'">net8.0-windows</TargetFramework>
<TargetFramework Condition="'$(RevitVersion)' == '2026'">net8.0-windows</TargetFramework>
<TargetFramework Condition="'$(RevitVersion)' &gt; '2026'">net10.0-windows</TargetFramework>
```

同时注入编译符号 `REVIT_2024` / `REVIT_2025_OR_GREATER` / `REVIT_NET8_OR_GREATER` 等，
供代码里做 `#if` 分支。

**输出目录按版本隔离**（`bin\2024\`、`bin\2025\`），
避免"2024 的 DLL 被装进 2025 目录"这种最难查的事故。

> 为什么不用 MSBuild 的 Multi-Target（`net48;net8.0-windows`）一次编完？
> 因为它把两个 DLL 放进同一个输出目录，而 `.addin` 清单只能指向一个。
> 装机时靠人工区分，迟早装错。宁可多跑一次 build，也要让"哪个 DLL 属于哪个版本"永远清楚。

### 2.2 代码：所有版本相关 API 收进 `Compat.cs`

业务代码**一行 `IntegerValue` 都不许出现**。新增 `addin/RevitWy.Plugin/Compat.cs`：

| 兼容点 | 2022–2023 | 2024 | 2025+ |
|---|---|---|---|
| 取 ElementId 数值 | `IntegerValue` | `Value`（`IntegerValue` 废弃） | `Value`（64 位，`IntegerValue` 会抛） |
| 造 ElementId | `new ElementId(int)` | 同 | `new ElementId(long)` |
| 判断类别 | 比较 `ElementId` | 同 | 同 |

调用方式是统一的：

```csharp
Compat.IdOf(element);                    // 取数值，永远安全
Compat.IsCategory(e, BuiltInCategory.OST_Walls);   // 判断类别
Compat.GetComments(e); / Compat.SetComments(e, s); // 读写构件标记
```

### 2.3 顺手修掉的一个真 bug

原来 `KindOf()` 是这么写的：

```csharp
var cat = e.Category != null ? e.Category.Id.IntegerValue : 0;
if (cat == (int)BuiltInCategory.OST_Walls) return "walls";   // ← 永远不成立
```

`(int)BuiltInCategory.OST_Walls` 是 **-2000011**（BuiltInCategory 是负数枚举），
而 `ElementId.IntegerValue` 是文档分配的正数，两者**永远不相等**。
后果：工作台点构件联动时，`kinds` 过滤实际从未生效——
只是因为 id 本身唯一，才没被发现。这次改成比较 `ElementId`，顺便解决
2024 废弃 / 2025 抛异常两个问题。

### 2.4 部署：按版本落到各自目录

```
%APPDATA%\Autodesk\Revit\Addins\2022\RevitWy.Plugin.addin
%APPDATA%\Autodesk\Revit\Addins\2024\RevitWy.Plugin.addin
%APPDATA%\Autodesk\Revit\Addins\2025\RevitWy.Plugin.addin
        └── revit-wy\RevitWy.Plugin.dll   ← 每个目录放**该版本编译的那个** DLL
```

`.addin` 清单是同一份（内容与版本无关），只是放进的目录不同。

### 2.5 一键构建：自动识别已装版本

```powershell
.\scripts\build-addin.ps1              # 编译本机装了的全部版本（2022+）
.\scripts\build-addin.ps1 -Deploy      # 编译并部署到各自目录
.\scripts\build-addin.ps1 -RevitVersions 2024 -Deploy
.\scripts\build-addin.ps1 -UseNuget -RevitVersions 2022,2025   # 没装 Revit 也能编（CI）
```

脚本会检查 .NET SDK：net48 要 SDK 6+，net8 要 SDK 8+，net10 要 SDK 10+。
SDK 不够的版本会被**跳过并说明原因**，不会假装成功。

## 三、Python 侧改了什么

IR（中间表示）本身是**版本中立**的：单位统一 mm、几何是坐标、字段是构件语义，
不依赖 Revit 年份。所以 Python 侧几乎不用改，只动了三处口径：

1. `target_revit_version` 默认从写死的 `"2022"` 改为 **`auto`**——
   含义是"以插件实际连接的版本为准"。硬编码某一年，换版本后报告会误导。
   也可以显式配成 `"2024"` 用于对账。
2. `revit-wy doctor` 增加 `revit_versions_installed`，列出本机装了哪些版本。
3. `revit-wy diag` 的 Revit 段改成"支持 2022 及以上"，并对每个版本标出
   **它需要哪个目标框架**；还会检查"装了但没部署插件"的版本并提示补齐。

## 四、怎么验证（按可信度从高到低）

| 级别 | 做法 | 能证明什么 |
|---|---|---|
| **编译期** | 每个版本的 `dotnet build` 都过 | API 差异都处理了（这是最容易漏的） |
| **加载期** | 装进对应版本目录，功能区出现 revit-wy 页签 | 运行时与清单都对了 |
| **功能期** | 点「连接状态」显示 Listening + `revit-wy status` 连上 | 协议层通 |
| **建模期** | 跑一张图 `--dry-run` 再 `--send`，看构件数与几何 | 建模逻辑在真版本上成立 |

前两级是硬门槛——**编译过不了、加载不出现，后面都无从谈起**。

## 五、当前状态的诚实说明

- **代码层面**：多版本支持已落地（csproj 多目标 + `Compat.cs` + 部署脚本 + 诊断）。
- **验证层面**：本仓库的 CI 环境没有 Windows 也没有 Revit，所以
  **只在语法/结构层面校验过（C# 解析 0 错误）**，没有真机编译与加载验证。
  这部分必须在你机器上跑一次 `.\scripts\build-addin.ps1 -Deploy` 才算数。
- **版本优先级**：2022 与 2024 是设计院主流，2025/2026 是新装机器。
  如果你手上是 2024，先只验 2024，别一次性铺开。

### 你机器的具体情况（Revit 2024）

诊断显示只有 Revit 2024，没有 2022。那么：

```powershell
# 1) 只编 2024（走 NuGet 也行，不依赖本机 API 路径）
.\scripts\build-addin.ps1 -RevitVersions 2024 -Deploy

# 2) 重启 Revit 2024，功能区应出现 revit-wy
# 3) 验证
.venv\Scripts\python -m revit_wy.cli status
```

Revit 2024 仍在 .NET Framework 4.8 线上，所以**代码路径与 2022 完全一致**，
预期一次编译就能过。真正需要额外验证的是 2025+（.NET 8 线）。
