# 模型体检与数据治理（试点第一阶段）

> 对应团队试点建议的**第一阶段 1–2 周**：MCP 自动巡检模型的无用视图 /
> 错漏参数 / 不合规族命名，一键导出结构化审计清单或批量修正属性。
>
> **风险等级：零建模破坏**。巡检全程只读；批量修正只动三个文本参数。

---

## 一、为什么先做这件事（而不是先翻模）

翻模是"从无到有"，任何一次试跑都要真建构件，错了就得撤；
模型体检是"从乱到清"，**读一遍、列清单，最坏的结果也只是清单里多几条误报**。

对设计院来说，这件事还有一个额外好处：它不依赖你现在用的图层规范。
不管图纸是谁画的、CAD 规范多乱，模型里已有的东西都能查。
所以它适合当**第一个能让团队看见结果**的动作。

| | 翻模（第二阶段） | 体检（第一阶段） |
|---|---|---|
| 前置条件 | 图必须规范、必须锁定单专业 | 打开模型就能跑 |
| 出错代价 | 建错构件 → 撤、重来 | 清单不准 → 改规则重跑 |
| 首次见效 | 需要校准图层规范（数天） | 第一次跑就出数字 |
| 谁会用 | 建模的人 | 项目负责人 / BIM 主管 |

## 二、能力范围：查什么、不查什么

### 已实现的 8 条规则

| 规则 | 级别 | 查什么 | 建议动作 |
|---|---|---|---|
| `VIEW-001` | 警告 | 不在任何图纸上的视图（三维/图例/明细表除外） | 删或放上图纸 |
| `VIEW-002` | 警告 | 空视图（0 个元素） | 删或确认漏画 |
| `VIEW-003` | 提示 | 视图名不含"平面/立面/剖面/三维/详图"等关键词 | 按「楼层-专业-类型」改名 |
| `VIEW-004` | 警告 | 只剩 ≤3 个元素但有标注（删模型留标注） | 清理 |
| `PARAM-001` | 警告 | 墙/柱/梁/门/窗/板 缺「标记」 | 批量填标记 |
| `PARAM-002` | 提示 | 任意构件缺「注释」 | 批量补注释 |
| `FAMILY-001` | 警告 | 族/类型名含空格、括号、斜杠等特殊字符或超长 | 按「专业_构件_尺寸」改名 |
| `FAMILY-002` | 提示 | 类型实例数为 0（未被使用） | 清理减体积 |

### 明确**不**做（第一阶段）

- **不删任何东西**。空视图、无用类型只进清单，删除必须人来点。
- **不改几何**。墙厚、柱位、标高一律不碰。
- **不改类型**。类型替换会连带算量口径变化，风险不是"删个空视图"能比的。
- **不判断"对不对"**。它只判断"缺不缺、规范不规范、用没用过"，
  不判断你的墙是不是画在正确位置——那需要设计意图，机器不知道。

## 三、四个入口

### 1. 命令行（最适合先试试）

```bat
:: 只读巡检，出终端报告
revit-wy audit model

:: 出 Markdown + HTML（HTML 是单文件，能直接发微信/邮件给领导）
revit-wy audit model --md reports\体检.md --html reports\体检.html

:: 没有 Revit 也想看报告长什么样（内置仿真数据，会明确标注"仿真"）
revit-wy audit model --demo

:: 导出 JSON + CSV（CSV 带 BOM，Excel 打开不乱码），给团队分派整改
revit-wy audit csv --out reports

:: 批量补标记：默认干跑，只告诉你将改多少个
revit-wy audit fix --ids 1001,1002 --param mark --value 待补
:: 确认无误加 --apply 才真的写
revit-wy audit fix --ids 1001,1002 --param mark --value 待补 --apply
```

### 2. 双击

`一键启动.bat` 里已经能看到 `audit` 相关的路径；如需给不写命令的同事用，
可另存一个 `一键体检.bat`，内容一行：`revit-wy audit model --html reports\体检.html`。

### 3. MCP（接 Cursor / WorkBuddy）

| 工具 | 说明 |
|---|---|
| `rwy_audit_model` | 巡检，返回健康分 + 问题清单 + 可批量修正的 id；`html_path`/`markdown_path` 可直接落盘 |
| `rwy_fix_issues` | 批量改白名单参数，`apply` 默认 `false`（干跑） |
| `rwy_export_audit` | 导出 JSON + CSV |

在 Cursor 里直接说人话：
> 「巡检一下当前模型，把问题按规则汇总，再把缺标记的构件批量补成"待补"。」

模型会自己走 `rwy_audit_model` → 读 `fixable.auto_fixable_ids` → `rwy_fix_issues`。
因为是干跑默认，它会先把计划说给你，你说"执行"它才带上 `apply=true`。

### 4. Revit 插件协议（`audit_model` / `fix_issues` / `export_audit`）

如果不用 MCP，任何能发 TCP JSON 的程序都能调，协议见 `docs/04`。

## 四、架构：为什么判定放在 Python 而不是插件里

```
Revit 插件（C#）          只负责"捞事实"
   FilteredElementCollector → views / elements / types
        │  TCP JSON
        ▼
Python（audit.py）        负责"判问题"
   8 条规则 → 问题清单 → 健康分 → Markdown / HTML / CSV
```

三个理由：

1. **改规则不用重编译 DLL**。各院命名规范不一样，改一条规则就要求
   重新编译、重新部署、重启 Revit，没人会去改第二次。
2. **能在没有 Revit 的机器上跑测试**。规则是最容易被信任也最容易写错的部分，
   本项目为它写了 24 个单元测试。
3. **跨版本风险最小**。C# 侧只有 `FilteredElementCollector` 这类 2022 到 2026
   都没变过的 API，判断逻辑零 Revit 依赖。

## 五、健康分怎么算（可质疑、可改）

```
密度 = (警告数 × 1.0 + 提示数 × 0.3) ÷ max(10, 对象总数 / 100)
分数 = round(100 × exp(−密度 / 12))
```

实测对照（100 个构件、4 个视图的模型）：

| 缺标记比例 | 分数 |
|---|---|
| 0 | 100 |
| 10% | 92 |
| 33% | 76 |
| 80% | 51 |

**为什么用指数曲线**：线性扣分下"三成构件缺参数"会和"全错"一样落到 0 分，
分数失去区分度。指数曲线保留差距，又不会把轻微遗漏打成不及格。

**为什么警告权重大于提示**：`PARAM-001`（缺标记，影响算量对账）确实比
`PARAM-002`（缺注释，只影响追溯）更值得修。权重 1.0 : 0.3 是经验值，
改 `audit.py::_score` 里两个数字即可，测试会兜住区间。

**这套口径是可以被质疑的**——如果你的项目认为命名规范比缺参数更重要，
把 `RULES` 里的 `level` 从 `info` 提到 `warn` 就行，分数会立刻变化。

## 六、批量修正的安全边界

```json
{"ids": [1001, 1002], "param": "mark", "value": "待补", "apply": true}
```

- `ids` **必须显式给出**，不接受"全部"、"所有缺参数的"这类模糊条件。
  理由：模糊条件一旦规则误判，就会成批写错。
- `param` 只接受 `mark` / `comments` / `description` 三个：
  - `mark`（标记）→ 出图与算量对账
  - `comments`（注释）→ 追溯来源（比如"来源图层 A-WALL"）
  - `description`（说明）→ 补充描述
- `apply` 默认 `false`。干跑会返回 `would_change` 数量和样本，
  确认后才落笔。
- 每个 id 单独 `try/catch`，一个失败不影响其余，失败原因回传。

**几何、类型、视图结构不在此入口内**——它们需要单独的、带人确认的入口，
这是刻意留的空白，不是没做完。

## 七、效率账（可核对的口径）

基线在 `config/effort_baseline.yaml`：

```yaml
audit_seconds_per_element: 4    # 人工看一个构件的参数要 4 秒
audit_seconds_per_view: 20      # 人工判断一个视图要 20 秒
```

内置仿真模型（250 构件 / 5 视图）实测：

| 项 | 数值 |
|---|---|
| 人工逐条核对 | 18.3 分钟 |
| 自动巡检 | 5.1 秒 |
| 净节省 | 18.2 分钟 |

**口径说明（必须一起说，否则数字会被质疑）**：
- 只算**核对**，不算**修复**。修复要人判断该填什么值，机器替代不了。
- 4 秒/构件是"打开属性面板、扫一眼、判断"的经验值。真实项目里
  工程师不会逐个看——他们是按经验抽查。所以这个数字代表的是
  "如果要把每个构件都核一遍需要多久"，不是"你现在浪费了多少时间"。
- 基线可改。如果你们认为 2 秒更准，改 YAML 后所有报告自动跟着变。
